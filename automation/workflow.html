Konsep Workflow

Workflow adalah rangkaian langkah terdefinisi yang mengubah input menjadi output melalui serangkaian proses. Dalam konteks AI automation, workflow menggabungkan LLM calls, API integrations, data transformations, dan decision logic dalam alur yang dapat dijalankan, dipantau, dan di-debug.

Setiap workflow memiliki tiga komponen inti: trigger (apa yang memulai), steps (rangkaian tindakan), dan state (konteks yang mengalir antar langkah). Kualitas workflow ditentukan oleh seberapa baik ketiga komponen ini dirancang dan di-instrument.

5 Pola Workflow

1. Sequential Pipeline

Langkah berurutan: A -> B -> C. Output setiap langkah menjadi input langkah berikutnya. Pola paling sederhana dan paling umum. Cocok untuk tugas linear di mana setiap langkah bergantung sepenuh pada langkah sebelumnya.

def content_pipeline(topic):
 # Step 1: Research
 research = llm.complete(
 f"Riset topik: {topic}. Berikan 5 key points."
 )
 
 # Step 2: Draft
 draft = llm.complete(
 f"Tulis artikel 500 kata berdasarkan: {research}"
 )
 
 # Step 3: Polish
 polished = llm.complete(
 f"Edit untuk grammar, clarity, dan flow: {draft}"
 )
 
 # Step 4: Publish
 cms.publish(title=topic, content=polished)
 return polished

Best practices: Set timeout per step, log input/output setiap step, implement retry dengan backoff, dan untuk setiap step idempotent jika memungkinkan.

2. Parallel Execution

Multiple langkah berjalan simultan, hasil dikumpulkan. Cocok ketika langkah-langkah independen dan tidak saling bergantung. Mengurangi total latency secara signifikan.

import asyncio

async def enrich_lead(lead):
 # Run independent enrichments in parallel
 company_info, social_data, news = await asyncio.gather(
 fetch_company_info(lead["company"]),
 fetch_social_profiles(lead["name"]),
 search_recent_news(lead["company"]),
 return_exceptions=True # Don't fail all if one fails
 )
 
 return {
 **lead,
 "company": company_info,
 "social": social_data,
 "news": news,
 }

Best practices: Gunakan return_exceptions=True agar satu failure tidak membatalkan semua, set concurrency limit untuk menghindari rate limit, dan kumpulkan partial results.

3. Conditional Branching

Alur bercabang berdasarkan kondisi. Decision point dapat berupa rule-based (if-else) atau AI-driven (LLM klasifikasi). Cocok untuk workflow yang membutuhkan routing dinamis.

def route_ticket(ticket):
 # AI-powered classification
 classification = llm.complete(
 f"Klasifikasi tiket: {ticket['content']}\n"
 f"Kategori: technical|billing|general\n"
 f"Severity: low|medium|high|critical\n"
 f"Format: category|severity"
 )
 
 category, severity = classification.strip().split("|")
 
 if severity == "critical":
 notify_oncall(ticket, category)
 escalate_to_senior(ticket)
 elif category == "billing":
 route_to_billing_team(ticket)
 elif category == "technical":
 if severity in ("high", "medium"):
 route_to_tech_team(ticket, priority=severity)
 else:
 auto_respond_with_kb(ticket)
 else:
 queue_for_manual_review(ticket)

Best practices: Selalu memiliki default/fallback branch, log setiap decision point dengan alasan, dan batasi kedalaman branching untuk menghindari kompleksitas yang tidak terkelola.

4. Loop dengan Exit Condition

Ulangi rangkaian langkah hingga kondisi terpenuhi: quality threshold tercapai, maksimum iterasi, atau konvergensi. Cocok untuk iterative refinement.

def iterative_refine(content, max_iterations=5):
 quality_score = 0
 iteration = 0
 
 while quality_score < 0.85 and iteration < max_iterations:
 # AI evaluates quality
 evaluation = llm.complete(
 f"Nilai kualitas artikel (0-1): {content}\n"
 f"Format: score|issues|suggestions"
 )
 score, issues, suggestions = evaluation.split("|")
 quality_score = float(score)
 
 if quality_score < 0.85:
 # AI refines based on feedback
 content = llm.complete(
 f"Tingkatkan artikel berikut.\n"
 f"Issues: {issues}\n"
 f"Suggestions: {suggestions}\n"
 f"Artikel: {content}"
 )
 
 iteration += 1
 
 return content, quality_score, iteration

Best practices: Selalu set maksimum iterasi untuk mencegah infinite loop, log setiap iterasi untuk debugging, dan implement timeout per iterasi.

5. Fan-Out / Fan-In

Pecah tugas besar menjadi sub-tugas paralel, proses secara simultan, lalu kumpulkan dan agregasi hasil. Cocok untuk batch processing dan MapReduce patterns.

async def batch_process_documents(documents):
 # FAN-OUT: Split documents into chunks
 chunks = []
 for doc in documents:
 doc_chunks = split_into_chunks(doc, chunk_size=4000)
 chunks.extend(doc_chunks)
 
 # Process all chunks in parallel
 tasks = [process_chunk(chunk) for chunk in chunks]
 results = await asyncio.gather(*tasks)
 
 # FAN-IN: Aggregate results
 by_document = group_by_document(results, chunks)
 
 final_summaries = {}
 for doc_id, chunk_results in by_document.items():
 # Merge chunk results into single summary
 merged = llm.complete(
 f"Gabungkan hasil berikut menjadi ringkasan "
 f"koheren: {chunk_results}"
 )
 final_summaries[doc_id] = merged
 
 return final_summaries

Best practices: Set concurrency limit (e.g., 10 parallel), implement backpressure jika queue terlalu panjang, dan untuk aggregation logic yang dapat menangani partial failures.

Event-Driven vs Scheduled

Scheduled (Cron-based)

Workflow berjalan pada interval tetap: setiap menit, jam, hari, atau minggu. Cocok untuk tugas yang tidak bergantung pada event real-time: report generation, data sync, cleanup.

# Hermes cron example
schedule: "0 9 * * *" # Every day at 9 AM
task: "generate_daily_report"
config:
 report_type: "executive_summary"
 recipients: ["team@company.com"]

Kelebihan: Prediktable, mudah di-debug, resource planning mudah. Kekurangan: Tidak real-time, potential delay, wasted runs jika tidak ada data baru.

Event-Driven

Workflow dipicu oleh event: webhook diterima, file diupload, database row berubah, message queue. Cocok untuk tugas real-time: notification, sync, processing.

# Webhook-triggered workflow
@app.post("/webhook/github")
async def github_webhook(payload):
 if payload["action"] == "opened":
 # New PR opened -> trigger review workflow
 await trigger_workflow(
 "pr_review",
 pr_data=payload["pull_request"]
 )
 return {"status": "triggered"}

Kelebihan: Real-time, efisien (hanya berjalan saat perlu). Kekurangan: Lebih kompleks, race condition possible, perlu message queue untuk reliability.

Hybrid Approach

Kombinasi: event-driven untuk real-time processing, scheduled untuk batch dan retry. Contoh: webhook menambah task ke queue, scheduled worker memproses queue setiap 5 menit.

State Management

Stateless

Setiap run workflow independen, tidak ada konteks dari run sebelumnya. Cocok untuk tugas yang self-contained: transformasi data, one-shot generation.

Kelebihan: Sederhana, mudah di-scale, tidak ada state corruption. Kekurangan: Tidak dapat menangani multi-step async atau resumption.

Stateful (Persistent)

Konteks disimpan antar step dan antar run. Diperlukan untuk workflow multi-step async, human-in-the-loop, atau resumption setelah failure.

# Temporal-style stateful workflow
@workflow.defn
class OrderWorkflow:
 @workflow.run
 async def run(self, order_id: str):
 order = await workflow.execute_activity(
 fetch_order, order_id
 )
 
 # Human approval step (may take hours/days)
 approved = await workflow.execute_activity(
 wait_for_approval, order, 
 start_to_close_timeout=timedelta(days=7)
 )
 
 if approved:
 await workflow.execute_activity(
 process_payment, order
 )
 await workflow.execute_activity(
 ship_order, order
 )
 else:
 await workflow.execute_activity(
 cancel_order, order
 )

Event-Sourced

Semua events dicatat sebagai log immutable. State direkonstruksi dengan replay event log. Memberikan audit trail lengkap dan memungkinkan time-travel debugging.

Error Handling dalam Workflow

Retry dengan Exponential Backoff

import asyncio
import random

async def with_retry(func, max_retries=3, base_delay=1):
 for attempt in range(max_retries):
 try:
 return await func()
 except Exception as e:
 if attempt == max_retries - 1:
 raise
 delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
 await asyncio.sleep(delay)

Dead Letter Queue

Pesan yang gagal setelah max retries dipindahkan ke DLQ untuk investigasi manual, bukan dibuang.

Circuit Breaker

Jika error rate melebihi threshold, stop workflow sementara untuk mencegah cascade failure.

class CircuitBreaker:
 def __init__(self, threshold=5, reset_timeout=60):
 self.failures = 0
 self.threshold = threshold
 self.reset_timeout = reset_timeout
 self.last_failure = None
 
 def can_execute(self):
 if self.failures < self.threshold:
 return True
 # Check if reset timeout has passed
 if time.time() - self.last_failure > self.reset_timeout:
 self.failures = 0
 return True
 return False
