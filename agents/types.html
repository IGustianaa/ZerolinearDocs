Klasifikasi Berdasarkan Arsitektur

AI Agent dapat diklasifikasikan berdasarkan bagaimana mereka memproses informasi dan mengambil keputusan. Tiga paradigma utama — reactive, deliberative, dan hybrid — mewakili trade-off fundamental antara kecepatan dan kedalaman penalaran.

Reactive Agent

Reactive agent merespons stimulus langsung tanpa membangun model dunia internal atau merencanakan ke depan. Setiap input dipetakan ke output melalui aturan atau model yang telah ditentukan. Keunggulan utama adalah kecepatan — tidak ada overhead komputasi untuk planning, sehingga respons dapat dihasilkan dalam milidetik. Kelemahannya: tidak dapat menangani tugas yang membutuhkan multiple dependent steps atau antisipasi konsekuensi jangka panjang.

Contoh: customer support bot yang mengklasifikasikan tiket ke departemen tertentu berdasarkan keyword. Setiap pesan diproses independen, tidak ada dependensi antar-pesan. Cocok untuk volume tinggi dengan kompleksitas rendah.

Deliberative Agent

Deliberative agent membangun representasi internal dari dunia, merencanakan rangkaian tindakan, mensimulasikan konsekuensi, dan memilih jalur optimal. Agen ini menggunakan LLM untuk reasoning multi-langkah sebelum bertindak. Keunggulannya: dapat menangani tugas kompleks yang membutuhkan dependensi antar-langkah, trade-off, dan antisipasi. Kelemahannya: lebih lambat (setiap planning step melibatkan LLM call) dan lebih mahal (token usage tinggi).

Contoh: research assistant yang menerima topik, menyusun rencana penelitian (sub-pertanyaan, sumber yang akan dicari, urutan analisis), lalu mengeksekusi rencana tersebut dengan koreksi adaptif.

Hybrid Agent

Hybrid agent menggabungkan kedua pendekatan: menggunakan reactive mode untuk tindakan yang sederhana dan mendesak, dan deliberative mode untuk keputusan strategis. Agen memilih mode berdasarkan kompleksitas tugas dan urgensi. Ini adalah arsitektur yang paling banyak digunakan dalam production — Hermes Agent misalnya, menggunakan reactive mode untuk tool calls rutin dan deliberative mode untuk planning task kompleks.

Assistant Level

Assistant adalah tingkat paling dasar. Pengguna memulai setiap interaksi, agen merespons dalam satu atau beberapa turn. Tidak ada inisiatif dari agen. Cocok untuk: penulisan, analisis, coding assistance di mana pengguna ingin kontrol penuh atas proses.

Task Agent Level

Task agent menerima tujuan tingkat menengah, memecah menjadi sub-tugas, dan mengeksekusi dengan checkpoint approval. Pengguna dapat mengintervensi di milestone tertentu. Cocok untuk: software engineering (review PR sebelum merge), data analysis (konfirmasi asumsi sebelum eksekusi), content creation (approval outline sebelum writing).

Autonomous Agent Level

Autonomous agent berjalan mandiri setelah diberi tujuan dan batasan. Bisa berjalan 24/7, memantau sistem, dan mengambil tindakan tanpa approval per-step. Cocok untuk: monitoring infrastruktur (deteksi anomali dan auto-scale), social media management (posting terjadwal), data pipeline (ETL dengan error recovery). Risiko lebih tinggi, sehingga guardrails wajib: max iterations, action whitelist, alerting.

Multi-Agent Level

Multi-agent system melibatkan beberapa agen yang berkolaborasi, masing-masing dengan spesialisasi. Bisa berstruktur hierarki (orchestrator + workers), peer-to-peer (agen berdebat/mendiskusikan), atau market-based (agen "mengajukan bid" untuk tugas).

Multi-Agent Systems

Hierarchical (Orchestrator-Worker)

Satu agen orchestrator menerima tujuan, memecah menjadi sub-tugas, dan mendelegasikan ke worker agents. Setiap worker memiliki spesialisasi: researcher, coder, reviewer, tester. Orchestrator mengumpulkan hasil, mengevaluasi, dan menyusun output akhir.

Keunggulan: kontrol terpusat, mudah di-debug, cocok untuk pipeline linear. Kelemahan: orchestrator menjadi bottleneck, single point of failure.

Peer-to-Peer (P2P)

Agen berkomunikasi secara horizontal tanpa orchestrator. Setiap agen dapat mengirim pesan ke agen lain. Cocok untuk: debat (dua agen dengan perspektif berbeda mencapai konsensus), brainstorming (multiple agen mengusulkan solusi, voting).

Keunggulan: lebih kreatif, tidak ada bottleneck. Kelemahan: sulit dikontrol, konvergensi tidak dijamin, token usage tinggi karena banyak pesan antar-agen.

Market-Based

Agen "mengajukan bid" untuk tugas berdasarkan kapabilitas dan beban kerja. Orchestrator memilih bidder terbaik. Cocok untuk: sistem dengan beban variabel di mana agen memiliki kapabilitas overlap.

Specialist Teams

Tim agen dengan peran tetap: Researcher (mencari data), Writer (menyusun), Editor (merevisi), Publisher (menyimpan dan distribusi). Mirip dengan tim editorial di media. Framework seperti CrewAI dirancang khusus untuk pola ini.

Pertimbangan Tambahan

  • Biaya — Multi-agent menggunakan 3-10x lebih banyak token dibanding single agent. Setiap interaksi antar-agen adalah LLM call. Pastikan ROI jelas: jika single agent bisa menyelesaikan 80% task, multi-agent hanya untuk 20% sisanya.
  • Latency — Setiap LLM call menambah 0.5-10 detik. Multi-agent berurutan bisa 30-60 detik per task. Paralelisasi membantu tetapi koordinasi tetap butuh overhead. Untuk real-time application, pertimbangkan hybrid: reactive untuk response cepat, deliberative untuk task kompleks di background.
  • Complexity — Debugging multi-agent jauh lebih sulit dari single agent. Interaksi antar-agen menciptakan emergent behavior yang sulit diprediksi. Mulai dengan single agent, split hanya jika diperlukan dan setelah memahami failure modes.
  • Observability — Setiap agen harus log reasoning, tool calls, dan results secara terstruktur. Tanpa logging komprehensif, mustahil men-debug masalah atau meningkatkan kualitas. Investasi di observability dari hari pertama.
  • Token budget — Tetapkan budget token per task. Jika agen melebihi budget, hentikan dan escalate. Mencegah cost overrun dari loop yang tidak konvergen.
  • Evaluation — Definisikan metric sukses sebelum deploy. "Akurasi" saja tidak cukup — tambahkan latency, cost per task, dan user satisfaction. A/B test agent configurations secara sistematis.

Anti-Patterns yang Harus Dihindari

  1. Agent maximalism — Tidak semua masalah butuh agen. Jika task bisa diselesaikan dengan script deterministic atau rule-based, jangan gunakan LLM agent. Agent untuk kompleksitas yang tidak dapat di-hardcode.
  2. Premature multi-agent — Mulai dengan multi-agent terlalu cepat. Selalu mulai dengan single agent, evaluasi, dan split hanya jika bottleneck teridentifikasi.
  3. Missing guardrails — Deploy agen otonom tanpa batas iterasi, action whitelist, atau human approval. Resiko: agen mengambil tindakan destruktif atau menghabiskan budget dalam loop tak terbatas.
  4. No fallback — Agen yang crash tanpa recovery strategy. Selalu memiliki rencana: retry, fallback ke model lain, atau return partial result dengan flag.

Pilihan tipe agen harus didasarkan pada kebutuhan tugas, bukan hype. Untuk 80% use case production, single deliberative agent dengan 5-10 tools sudah memadai. Multi-agent system hanya diperlukan ketika tugas benar-benar membutuhkan spesialisasi peran atau paralelisme yang tidak dapat dicapai dengan satu agen. Evaluasi secara berkala: apakah kompleksitas saat ini masih justified, atau dapat disederhanakan?
